# Production user-workload load test — 2026-09-18

## Result

The Anansi production replica sustained **250 complete screen loads per
second**, or about **1,416 authenticated API requests per second**, with no
failed or dropped requests, 14.77 ms request p95, and 26.86 ms full-screen p95
in the repeatable steady run.

At an aggregate 400 offered screen loads per second from two synchronized load
generator processes, the replica completed 2,061 requests per second. Request
p95 rose to about 610 ms, full-screen p95 reached 1.67 seconds, and 635 of
12,000 offered sessions were dropped by the generators. The capacity knee is
therefore between 250 and 400 screen loads per second.

For operating headroom, **150 screen loads per second / 837 requests per
second** remains the conservative single-replica planning figure. It kept
full-screen p95 at 7.74 ms during the ramp. The 250 screen-load/s result is a
measured low-latency maximum, rather than the recommended sustained target.

## Workload

The test used valid short-lived access tokens and 100 isolated synthetic
households. Each household was seeded through the deployed API with shopping
list items, chores, expenses, and pinwall posts. Weighted virtual sessions
loaded the same read endpoints used by the app's Home, Lists, Chores, Money,
Recipes, and Calendar screens.

The corrected runner uses a stable pool of 7,500 trusted virtual-user IPs. This
models users returning from the same address while keeping each address below
the production abuse budget. Requests went directly to the private backend
container to measure VPS/API/database capacity without Cloudflare or
public-network latency.

The tested node had 4 vCPUs (AMD EPYC 7543), 15 GiB RAM, and hosted the active
PostgreSQL primary. The backend image was
`56d91f75b11e1edb3798f1062d2712dd60554bcb`.

At overload, the original single Python process consumed nearly one full CPU
core and shed new sessions after its concurrency queue filled. Its 1,400–1,500
requests/s plateau was a generator limit as well as a server limit, so the
rows above 250 screen loads/s do not represent a hard API throughput ceiling.
The zero HTTP-error result means admitted API requests remained stable; it does
not mean the replica accepted all offered sessions.

Calendar aggregation was the slowest route near the capacity knee at 16.63 ms
p95. Under the 1,500 screen-load/s overload it reached 529.87 ms p95.

## CPU diagnosis

The backend container has no cgroup CPU quota: `cpu.max` is `max 100000`, its
allowed CPU list is `0-3`, and the process sees four CPUs. `GOMAXPROCS` is not
set, so Go uses the available CPU count. The approximately 100% backend reading
means one core's worth of API work, not 100% of the four-core VPS.

A focused 250 screen-load/s run measured:

| Process/resource | Average CPU |
|---|---:|
| Go backend | 101.52% (1.02 cores) |
| PostgreSQL primary | 83.30% (0.83 cores) |
| On-box Python generator | 67.65% (0.68 cores) |
| Whole 4-vCPU host | 70.51% (2.82 cores) |

The synchronized two-generator 400 screen-load/s run measured:

| Process/resource | Average CPU |
|---|---:|
| Go backend | 118.37% (1.18 cores) |
| PostgreSQL primary | 118.27% (1.18 cores) |
| Two on-box Python generators | 99.50% (1.00 core) |
| Whole 4-vCPU host | 92.82% (3.71 cores) |

Real traffic originates off-server, so the generator's roughly one-core cost
does not apply in production. The measurements show hardware headroom and some
multi-core scaling, but the current API process does not scale linearly across
all four cores. Running multiple backend replicas on the node is likely to use
the spare cores more effectively, after the replica configuration issue below
is fixed and the shared database is measured under that topology.

Memory is not the current constraint. The backend used about 87 MiB at 250
screen loads/s and 133 MiB during the dual-generator overload on a host with
about 15 GiB RAM. CPU and request-path contention arrive first.

The initial runner assigned a new IP to every screen load. That exposed a real
high-cardinality behavior in the in-process rate limiter: after its 10,000
bucket cap, each new key scans and evicts while holding the global limiter
mutex. The runner now uses stable virtual-user IPs so that behavior does not
distort normal-user capacity. The limiter eviction path should still be
optimized separately because an IP spray can trigger it.

## Post-test checks

- `/healthz` and `/readyz` passed immediately after the overload run.
- All measured responses were HTTP 200.
- Synthetic data cleanup completed after every run.
- A direct database audit found zero remaining `mitlist-load-*` users.

## Production topology finding

The running Anansi backend has `TRUSTED_PROXIES=172.16.0.0/12`; the running
Fuwuqier backend does not have `TRUSTED_PROXIES` set. On Fuwuqier, requests
arriving through its Cloudflare Tunnel connector therefore share the
connector's source IP in the in-process 100-requests/minute IP limiter. This
must be corrected before the second replica can be tested as independent real
users or relied on for equivalent production traffic.

## Reproduction

The workload runner is `scripts/user-workload.py`. It requires explicit
`--allow-production-data`, uses an `example.invalid` address namespace, and
always runs cleanup in a `finally` block.
